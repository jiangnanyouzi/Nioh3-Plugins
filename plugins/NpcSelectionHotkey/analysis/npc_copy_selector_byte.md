# 复制外貌 NPC 选择:受控差分与写入链(2026-08-19/21,游戏 2.0.0.1)

> 方法:同一会话内对 `PlayerData` 全 0x3600 字节做多份快照(双基线噪声底 +
> npc1/npc2/npc3),扣除自然漂移后定位干净变化;再用硬件断点逐层追写入者。
> 快照文件:`snapshots/playerdata_{before,after,npc1,npc2}.bin`。
> 另一次会话(基址 0x7FF764D80000)完成写入链与模型引用追踪。

## 结论一:NPC 选择字节

```text
PlayerData + 0x248D   byte   复制外貌 NPC 选择(装备组 0)
PlayerData + 0x248E   byte   同上(装备组 1,实测恒写 0x00)
  0x00 = 原本样貌
  0x67 = npc1   0x81 = npc2   0x9F = npc3
```

- 每次受控切换,PlayerData 中唯一的干净变化就是这个字节;liveState 幻化
  状态表全程零变化(复制外貌与幻化字是两套系统)。
- 差值不等(+0x1A/+0x1E),是各 NPC 的标识值而非列表序号。
- 上游来源(已 live 验证):`[[Nioh3.exe+0x4748820]] + 0x71AC + index`,
  当前激活值就躺在这里(npc3 时为 `9F 00`)。
- **2.0.0.2 复现(2026-08-21,基址 0x7FF6EF090000)**:上游全局漂移到
  `Nioh3.exe+0x4749830`(与 playerTableGlobal 0x473C308→0x473D318、
  appearanceStateGlobal 0x47484F0→0x4749500 同向 +0x1010);写入者
  `+0x571DFC`、调用点 `+0x57277D`、`+0x71AC` 偏移全部未变。硬件写断点
  捕获完整序列:`0x67`(npc1)→`0x81`(npc2)→`0x9F`(npc3)→`0x00`(原本),
  每次切换 2 次命中(与文档 8 次一致),RDX=写入值、RCX=PlayerData+0x590。
  快照差分(`npc0 vs npc1 vs npc0-final`)确认唯一干净变化仍是 `+0x248D`,
  其余 5 字节(0x0141/0x0142/0x0449/0x044A/0x0462)为持续漂移的动画计时
  噪声,与复制无关。
- **跨重启持久**(2026-08-21):重启游戏后该字节仍为 `0x67`(npc1),
  说明选择随存档保存/加载时重放。
- **切回原本样貌走同一路径**(2026-08-21):npc1 → 原本样貌 时同一调用点
  `+0x57277D` 同样命中 8 次,写入值就是 `0x00`。即"解除复制"与"复制 npc"
  共用同一同步事务,仅值不同。注意:切回时日志只出现装备/服装模型重载,
  身体模型 `0x4BA258DF` 不重读(见结论四更正)。

## 结论二:写字节不触发模型重建(实验证伪)

- 手动写 `+0x248D=0x67`,5 秒观察:字节不被回写、模型不变。
- 写字节 + F10(RefreshPlayerAppearance 路径,玩家更新线程):模型不变。
  说明 `+0x235092C` 的核心刷新不消费该字节。
- **2.0.0.2 更正(2026-08-21,插件实测)**:上面的"证伪"只对"单独写字节"
  成立;**完整四步链在玩家更新线程内执行时,画面真实切换**
  (npc1→npc2→npc3→原本,每次按 F6 画面立即变化):

  ```text
  1. 写上游选择表 [[0x4749830]]+0x71AC = 目标值(0x67/0x81/0x9F/0x00)
  2. 写 PlayerData+0x248D = 目标值
  3. 调外观同步器 +0x5725B0(PlayerData+0x590, 0)
  4. 调 RefreshPlayerAppearance +0x2351450
  ```

  关键差异:第 3+4 步必须由**游戏自身线程(玩家更新回调内)**执行;
  从 CE 外部线程调用同样的函数序列不生效(2026-08-21 实测:CE
  execute_code_ex 调同步器 + 提交函数均无画面变化)。插件
  `NpcSelectionHotkey`(hook `+0x84394` UpdateDispatcher,未占用)已验证
  该链;**无需 R9 条目对象、无需请求结构体 +0x2AA968/提交函数
  +0x2A9E34**——同步器 + 刷新即完成装备/服装模型重建。

## 结论三:字节写入路径(执行断点排除法)

写入者是 `Nioh3.exe+0x571DFC` 的边界检查字节写入
(`mov [rax+rcx+0x1EFD], dl`,RCX=PlayerData+0x590,RAX=组下标)。
其 4 个静态调用点中,UI 复制操作只命中 **`+0x57277D`**(其余三个
`+0x484A3A` / `+0x204A442` / `+0x21F2397` 均为 0 命中)。

该调用点所在函数是外观状态同步器,循环做三件事:

```text
1. liveState 记录同步:
   rax = [Nioh3.exe+0x47484F0]; rdx = [rax] + 0x23F9F0 + index*0x50
   rcx = rbx + 0x1F00 + index*0x50   (rbx = PlayerData+0x590)
   call +0x571D80                    ; 0x50 字节记录拷贝(条件不满足时清零 0x28 words)
2. 4 个全局标志字节 -> PlayerData+0x590+0x1FA0..0x1FA3
3. 选择字节:al = [[[Nioh3.exe+0x4748820]] + 0x71AC + index]
   -> writer -> PlayerData+0x248D/8E
```

`+0x284B804` 包装器 -> `+0x21F22E0` 事务(内部调与 RefreshPlayerAppearance
相同的核心 `+0x32572C`)在复制外貌操作中**零命中**,与 NPC 预设复制无关,
应归属其他功能(可能为"所遇玩家外观"类事务)。

## 结论四:身体模型引用与重建(写断点追踪)

玩家当前身体模型 KTID 的存储位置由 npc1→npc2 的 24 选 1 变化确认
(只有它跟随玩家切换):

```text
本会话:0x367A9FA910   npc1=0x3CA6B093 -> npc2=0xC317F9FA -> npc3=0x13A2F74A
```

更正(2026-08-21):此前把 `0xF9852E31` 标注为"原本样貌模型"证据不足,撤回。
经日志核对,玩家身体模型为 `0x4BA258DF.g1m`(1.1 MB),**只在启动读档时
加载一次**(07:19:24);切换 npc 与切回原本样貌均不重读它——切回只是重新
指向缓存中的身体模型,同时重读的是装备/服装模型。含义:身体 mod 文件在
磁盘上更新后,F10 与外观切换都不会让它生效,只能重启游戏;身体 mod 的
热重载需要强制该 KTID 资源失效并重新请求,本文未覆盖该路径。

切换时该字段的两次写入(npc2→npc3 捕获):

1. `+0x21AA73: mov [rbp+0x160], r15d(=0)` —— 先清零旧引用。
   所在代码连续初始化 ~0x790 字节结构体(多个字段清零、多个 float 置 -1.0),
   是**模型加载请求结构体的构造/重置**,rbp=0x367A9FA7B0(栈/池上临时对象)。
2. `+0xB946DA` 附近的通用属性 setter(`mov [rax], ecx; ret` 一族)——
   写入新 KTID,现场 RCX=0x13A2F74A(npc3)。该 setter 是通用属性系统
   thunk,调用者众多,不能直接当热键目标。

随后游戏按该请求结构体异步加载模型(`0x3CA6B093.g1m` 等 ModelData 加载日志)。

## 热键可行性评估与下一步

- 选择字节、上游全局表、同步器、模型 KTID 字段均已定位;但**重建由临时
  请求结构体驱动**,写字节/写 KTID 都不会单独触发重建。
- 可行方向:从通用 setter 的调用点向上回溯,找到"以 NPC 预设为参数构造并
  提交该请求结构体"的函数;若其参数仅是(目标玩家, 预设索引/KTID)且可在
  玩家更新线程调用,则可做热键。注意会话间 KTID/堆地址都会变,插件只能
  用 RVA + 指针链。
- 禁止事项:不要保存/重放任何 0x367… 栈地址;不要在非玩家更新线程调用
  事务函数;不要把 0x67/0x81/0x9F 当作稳定枚举(需映射表)。

## 2.0.0.2 补充:请求结构体构造函数参数可保存性(2026-08-21)

沿用"不找静态调用者,直接验证可保存参数"的思路,在 `+0x2AA968`
(模型加载请求结构体的构造/重置函数,入口 `push rbp`+`sub rsp,0xC28`+
`lea rbp,[rsp+0xD0]`,2.0.0.2 未漂移)入口挂执行断点,捕获 npc1→npc2
两次受控切换的实参:

| 参数 | npc1 现场 | npc2 现场 | 可保存性 |
| --- | --- | --- | --- |
| RCX | `Nioh3.exe+4BA7860` | 同 | ✅ 模块内静态对象(首字段虚表 `+0x2BAE4A8`) |
| RDX | 0 | 0 | ✅ 恒 0 |
| R8  | `0x1EC25549330` | 同 | ✅ `[Nioh3.exe+0x4751030]` 即此对象(模块链) |
| R9  | 堆对象 | 堆对象(变) | ❌ **唯一动态参数**(NPC 条目对象) |

R9 对象内容(两次对比):`+0x18` = 模块内代码指针 `+0x1F68000` 区域(不变),
`+0x20` = RCX 静态对象(不变),`+0x10/+0x28` = 堆指针(随 NPC 变)。R9
无模块静态区引用(8 字节全等 AOB 零命中)。含义:该函数/事务参数中 3/4
可经 RVA+指针链保存,但"目标 NPC 条目对象"必须由调用方提供、随切换
变化——游戏未预留稳定接口,与最初判断一致。

同步器(含 `+0x57277D` 调用点)入口 `+0x5725B0`,参数 `(RCX=PlayerData+
0x590, RDX=0/1)`,内部索引表全部是模块内静态地址(`0x7FF6F29FE788` 等)
——**输入全部可保存**,是本调查中参数最干净的调用点;但它只做字节同步,
不驱动重建(结论二/三),不适合直接当"复制 NPC"热键入口。

下一步建议(待实施):若要做热键,需先解决 R9 的来源——要么在会话内
捕获一次真实的"复制 npc"调用并缓存 R9(会话内有效,重启后失效),
要么放弃请求构造路径,改走 `body_asset_reload_chain.md` 的
DriverEntry(+0x1C2EE0C)重建链(该链参数同样需要条目对象,且版本失效
机制已实测可行)。

## 2.0.0.2 追加:R9 条目对象生命周期实测(2026-08-21)

对 npc2 的 R9 对象(`0x1ED0284E220`)挂 8 字节硬件写断点,切 npc3→
npc2 一次,捕获 **31591 次命中**——R9 **不是切换时创建/销毁的对象**:

- 写入者 1:`+0xD7FD0`(RVA 稳定)= 无锁原子计数器
  (`lock cmpxchg [rcx],...` 循环,高 32 位序号 +0x100000000、
  低 32 位掩码 0x7FFFFFFF),对 `[rcx]` 每帧高频更新——R9 首字段
  是"活跃序号",不是内容。
- 写入者 2:`+0x1B24BE`(RVA 稳定),RCX=0x21/0x01、R15=0x21/0x01
  按索引更新条目槽。
- 之前观察到 npc1 条目被"清零":是**原地清零**(对象未释放,地址仍
  可读,PAGE_READWRITE),非激活条目清空内容但**地址保持有效**。
- 含义:同一会话内 R9 地址不会因切换失效——缓存 3 个 NPC 条目地址
  (npc1/2/3 各捕获一次)即可供热键复用,无需重启级持久。

热键最终形态(**已实现并实测于 2026-08-21,插件 `NpcSelectionHotkey`**):
```text
热键 F6(玩家更新线程,通过 hook +0x84394 UpdateDispatcher):
 1. 写上游选择表 [[0x4749830]]+0x71AC = 目标值(0x00/0x67/0x81/0x9F)
 2. 写 PlayerData+0x248D = 目标值
 3. 调同步器 +0x5725B0(PlayerData+0x590, 0)
 4. 调 RefreshPlayerAppearance +0x2351450
 → 画面真实切换(np1/npc2/npc3/原本),每按一次立即生效
```

**重大简化**:无需 R9 条目对象、无需请求结构体 +0x2AA968 与提交函数
+0x2A9E34;同步器 + 刷新链在玩家更新线程内即可完成模型重建。
先前的"结论二证伪"与"R9 缓存方案"因此作废——R9 调查的教训是:
**所有游戏内函数调用必须在游戏自身线程执行,CE 外部线程调用即使
参数完全正确也不会生效**(2026-08-21 三次 CE 直测:写字节/同步器/
提交函数均无画面变化;同参数经插件在玩家更新线程执行即生效)。

**hook 冲突教训**(NpcSelectionHotkey 首版):`+0x8437C`(UpdateContextThunk)
与 `+0x84554`(UpdateSingleObject)函数头已被 AppearanceRefreshHotkey
改写为 jmp 跳板,新插件对同一地址做 Pattern 扫描必然失败(初始化返回
false,热键静默失效)。共存方案:hook 未被占用的 `+0x84394`
(UpdateDispatcher,UpdateContextThunk 每帧调用的分发器),签名
`48 89 5C 24 08 48 89 74 24 10 57 48 83 EC 20 4C 8B 01 48 8B F2 4D 85 C0`。
若未来 AppearanceRefreshHotkey 也占用该点,需重新选点或改用
"初始化阶段延迟 hook"策略。
