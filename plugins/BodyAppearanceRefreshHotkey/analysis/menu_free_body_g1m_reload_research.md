# 菜单外身体模型(0x4BA258DF.g1m)强制重载 — 逆向研究

目标:让 F9 在**无外观菜单**的情况下强制身体模型 `0x4BA258DF.g1m` 重载(外观数据不变也需重建)。

游戏版本 1.0.7.0。本基址 0x7FF6F3150000(可能随启动变化,以下均为 RVA = 绝对地址 − 基址)。

## 关键结论(已验证)

### 1. 插件原 F9 崩溃根因
插件旧版 `InvokeMenuFreeRefresh` 直接调用 `+0x225323C(0x64, 0x33)`。每次按 F9 崩溃
(SEH 0xC0000005 @ +0x22532AB)。崩溃链:
- `+0x225323C` 内部 `+0x3819AC0` **忽略入参,恒构造 desc={0x64, 0x33}**。
- `+0x381A4E4`(= `+0x39A4E4`):检查 `[0x7768398]`(globalRoot 非空)与 `[desc+4]`(非 0),
  `add rcx,0xB98`(调度对象)→ `jmp +0x6CA694`。
- `+0x6CA694`:哈希校验通过(`+0x6CA6C3` RAX=1),链表查找 `+0x6CA706` **找到已存在事件对象**。
- **事件已存在 → `+0x6CA70B: call +0x327769C`(状态查询)→ `+0x6CA710: xor eax,eax` 强制返回 0**。
- `+0x22532AB: mov [rax+0xAD2F],1` 遇 rax=0 → 崩溃。
- 事件**不存在**才走 `je +0x6CA727` → `call +0x381A988`(创建事务,返回新对象)。

即:菜单外调用该入口时事件通常已存在,返回 0 导致崩溃。**不可作为菜单外入口**。

### 2. `+0x381A988` = "创建+提交事件事务"入口
- `mov rcx,[rcx]`(dispatcher)→ `call [rax+0x28]`(edx=0xB578 创建)→ `+0x381BC2C`(body_tx)
  → `+0x381A9EC`(注册全局列表)。
- 正确参数:`rcx` = 调度对象(globalRoot+0xB98)、`rdx` = desc。
- **CE execute_code_ex 调用 `+0x381A988(调度对象, desc)` 成功**:触发 body_tx 1 次 +
  ModelData 外观模型重载,但 **不含 g1m**。UI 开启与否不影响。
- **结论:`+0x381A988` 只重载外观(装备)模型,与身体 g1m 无关。**

### 3. g1m 加载路径
- g1m 经 `+0x4E908`(EnqueueModelLoadByDesc)入队。BODY_ASSET_CONTEXT 的
  `archiveManager=0x26E3DA29330` = `+0x4E908` 调用时 r8 常量。
- `+0x4E908` 唯一直接调用者 `+0x3887986`(循环体 `mov rdx,rdi; mov rcx,rsi; call +0x4E908`)。
- 该循环是**加载请求处理**,空闲时**高频两路常量轮询**:
  - 路1: rcx=0x26E3CA045B0, rdx=0x26FC76A9480
  - 路2: rcx=0x26E3CA043D0, rdx=0x26FC76A8180
  - r8 恒 = 0x26E3DA29330(archiveManager)
- **断点 `+0x4E908` 或 `+0x3887986` 必卡**(每帧高频,回调即使最小也拖死游戏)。**不可用**。
- `find_call_references(+0x4E908)` 仅返回 1 个调用者。g1m 也走此循环,入队时 rdx 指向含
  0x4BA258DF 的 desc,但轮询槽与 g1m desc 难以区分,断点无法落地。

### 4. 触发源(已确认)
- **外观 UI 中切换身体选项 → g1m 加载**(日志 16:43:39、16:46:37 两次确认,含完整
  Nioh3 Female Nude Body .g1t 纹理)。
- **重进存档**也会触发 g1m 加载(玩家身体重建)。
- body_tx(30 次玩家加载)为外观事务,其 r8=0x33/0x32/0x30 是寄存器残留,非子码。

### 5. 其他确认
- `+0x327769C` = 状态查询函数(检查 `[0x75D3310]` 全局 + `[+0x1DC]` 标志),返回 bool,
  无刷新副作用。
- `+0x337CE60`(ctx 选择):`mov rax,[0x75C0F58]; cmp byte [rax+0xAC2],0; je → [rax+0x30](ctxA);
  否则 [rax+0x38](ctxB)`。
- 容器 `[0x7772CA0]` 运行时为空(仅加载时填充),不是玩家身体对象容器。
- `+0x21D10C`(DeserializeAsset)被 LooseFileLoader 钩住(`jmp 7FF6F312000A`),不可断点。
- LooseFileLoader 的 BODY_ASSET_RAW_STACK 是**原始栈值**,含数据段地址(如 0x7FF6F69055E7
  = "baseResourceInterface..." 字符串),非干净代码调用链,参考价值有限。

## 2026-08-14 新发现:静态事件模板表与完整加载路径

### 静态模板表(module .data,永不失效)

`+0x2253594` 初始化循环遍历的是**模块静态表**(RVA `+0x4376300`,
本会话绝对地址 0x7FF7858B6300)。每条 0x60 字节:

```text
entry+0x00  事件码 dword       entry+0x30  float 1.0(权重/标志)
entry+0x10  GUID (16字节)      entry+0x34  0xA12F3(域码?)
entry+0x20  ...                entry+0x44  float 10.3(边距)
                                 entry+0x50  子码 dword(如 0x65F34)
```

条目0 = **body 事件**: code=0x64, GUID `47C1ECCF-446A-72A0-47C3D1C3`,
float 1.0。加载时循环对 code 0x64 特判 `lea eax,[rcx-31]` → subcode 0x33。

### 加载期完整链(2026-08-14 断点验证)

```text
+0x21AC18 加载初始化
 → +0x2253594 遍历静态表[+0x3776300]
   → +0x22535F6 cmp ecx,0x64(特判)
   → +0x225360B call +0x225323C(key, subcode)
     → +0x6CA4E4 按 key 查 watcher(堆对象,消费后清空)
     → +0x6CA6A4 分发器 → +0x6CA988 创建+提交 → +0x6CBC2C body_tx
```

### 与本插件旧崩溃记录的合并结论

- 旧崩溃点 `+0x22532AB: mov [rax+0xAD2F],1`:watcher **已存在**时
  `+0x6CA6A4` 走 `+0x6CA70B` 状态查询返回 0 → 解引用 0 崩溃。
  事件不存在时正常创建。**菜单外 watcher 通常已存在 → 必崩**。
- `+0x6CA988(dispatcher, desc)` CE 实测可调:创建事务对象并直接
  `call +0x6CBC2C`(body_tx),注册到全局列表。不经过存在性检查。
  旧测试"不含 g1m"的原因存疑:desc 当时应为手工最小构造
  {0x64, 0x33},**缺静态表条目 0x10 的 GUID 与 0x30/0x34 字段**——
  `+0x6CBC2C` 内部如何消费这些字段决定了 g1m 是否重载,需用
  **完整静态条目**重新测试。
- desc 现在可以从静态表 `+0x3776300` 条目 0 **原样拷贝 0x60 字节**
  作为参数——这就是"游戏自有、永不过期"的 desc 来源。

## 2026-08-14 CE 实验:+0x6CA988 + 完整静态条目 desc

### 调用方式(已验证成功)

```text
desc  = Nioh3.exe+0x4376300 静态表条目0 的 0x60 字节副本(分配 RW 内存)
slot  = root+0xB98(其内容 = 调度对象本体;+0x6CA988 首指令 mov rcx,[rcx]
        会解引用,所以传 slot 地址本身)
call  = +0x6CA988(slot, descCopy)   // cdecl/x64, 同步执行
```

两次调用均无崩溃,返回堆事务对象。第二次在 `+0x6CBC2C` 断点确认:

```text
RCX = 0x2D63E30F0D0   ← 事务内部新建的 bodyParent 级对象(非玩家 bodyParent
                         0x2D63E006030——这是 CE 远程调用路径的临时事务对象)
RDX = descCopy
R8  = R9 = 0x33       ← 正确的 body 事务参数!
```

### 结论

- **+0x6CA988 + 完整静态条目 = 菜单外安全触发 body 事务**,参数
  R8=R9=0x33 与 UI/加载路径一致,无崩溃,游戏继续运行。
- RCX 与玩家 bodyParent 不同:CE 在独立线程/上下文执行,事务对象
  是新建的。**玩家可见模型是否被刷新待视觉确认**;若可见模型未变,
  需要确认事务如何路由到玩家(可能需在游戏主线程执行,或 RCX 应
  显式传玩家 bodyParent——+0x6CA988 内部 [rcx] 后 call [rax+28]
  创建的是新对象,事务对象即其返回值)。

## 2026-08-14 直接调用 +0x6CBC2C 实验(崩溃,重要负结果)

```text
execute_code_ex(+0x6CBC2C, RCX=玩家bodyParent, RDX=desc副本, R8=0x33, R9=0x33)
→ 断点确认入参正确执行 → 随后 root 全局被清空,进程退出。
```

### 结论(排除法收窄)

- `+0x6CBC2C` 在 UI/加载线程执行时用同样参数是安全的,在 CE
  远程线程执行则崩 → 该函数依赖**调用线程的上下文**(TLS/线程局部
  队列/渲染状态),不仅是寄存器参数。
- `+0x6CA988` 在 CE 线程安全但作用在游离事务对象上,不刷新玩家。
- **无菜单刷新必须在游戏线程内发起**。两个可行方向:
  1. 主线程排队:CE `queue_to_main_thread` / 游戏自有任务队列;
  2. AA 热键跳板:mid-hook 游戏每帧必经点(如 +0x22536E0 或
     +0x20D20B watcher 循环),置标志,游戏下帧在自己的线程里
     调 +0x6CA988(dispatcher, 静态表条目副本)。
     这与 F9 现有插件(mid-hook +0x225373E)同构,插件已有成熟模式。

## 2026-08-14 跳板实验失败记录(重要负结果)

### 候选挂点排查(新会话全部实测)

| 候选点 | 正常游戏空闲 3s 命中 | 结论 |
| --- | --- | --- |
| +0x20D20B watcher循环 | 0 | 仅加载/UI 时活动 |
| +0x6CA4E4 watcher查找 | 0 | 同上 |
| +0x22536E0 UI更新 | 0 | 仅 UI 打开时 |
| +0x970314 版本查询 | 0 | 同上 |
| +0x6CA988 事务创建 | 0 | 同上 |
| **+0x74AA4**(0x7FF7815C4AA4) | **49040/2s ≈ 24k/s** | 高频活跃,但远超帧率 → 疑似任务分发/多线程入口,非单一渲染循环 |

### AA 跳板崩溃原因(3 个叠加)

1. hook 点 +0x74AA4 频率过高(24k/s),对每次调用都执行 cmp+jne,
   且该函数带 stack canary(prologue `mov [rsp+50],rax` 写 canary)。
   跳板先执行 `sub rsp,60` 再跳回 +0x74AA8 → **canary 写到跳板栈帧**,
   函数 epilogue 校验失败 → __fastfail → 进程终止。
2. `lea rdx,[nmTrampoline+0x40]` 被 AA 汇编成 `lea rdx,[rip+0xFFFFFFFF64]`
   坏编码(标签解析问题),desc 指针指向非法地址。
3. desc 副本先写到了错误位置(alloc 的跳板内存与预分配 buffer 不是同一块),
   依赖外部 Lua 补写——流程本就不该这样。

### 修正方向(下次实验)

- 不 hook 带栈帧/canary 的函数入口,改 hook **无栈副作用的中段指令**
  (与 F9 插件 mid-hook +0x225373E 同思路),或用 **VEH/单次软断点**让
  游戏在下一次自然经过时执行注入调用。
- 跳板只做:cmp flag / jne / call / 清 flag / **原样执行被覆盖的指令** /
  jmp 回原地址,不改变栈布局。
- desc 直接用静态表地址 +0x4376300(模块内只读,无需副本)。
- 若 +0x6CA988 在游戏线程内仍只建游离事务(大概率),下一步应改为在
  游戏线程内直接调 +0x225323C(0x64,0x33) 前先调 +0x6CA4E4 检查
  watcher 状态,复刻加载路径的前置条件。

## 2026-08-14 第三轮:mid-hook 跳板再次崩溃(完整尸检)

### 挂点与字节码(已完整手工解码验证)

hook `+0x74AB2`(函数 +0x74AA4 中段,`mov [rsp+50],rax` + 
`mov rdi,[rcx+48]` 共 9 字节连续覆盖区,恢复后跳 +0x74ABB)。
该点 25k/s 多线程执行。

### 确定的三个问题

1. **打补丁竞态(本次崩溃主因)**:对 25k/s 热代码做 9 字节在线
   patch,写入瞬间有线程执行在补丁区 → 半旧半新指令流 → 崩溃。
   **正确流程必须:暂停进程所有线程 → 写补丁 → 恢复线程。**
   (CE auto_assemble 不保证此顺序,需 pause_process + 手动 write。)
2. **栈对齐 bug(已编码但未触发,flag 始终为 0)**:
   跳板内 7 push(56B)+ sub rsp,0x28(40B) = 96B → call 时
   rsp≡8 (mod16) 错误,应 sub rsp,0x20。被调函数 movaps 会 #GP。
3. 返回跳转写成 +0x74AB7 会重复执行 mov rdi,[rcx+48](幂等,瑕疵)。

### 关键新认识(对下一步至关重要)

- 第三轮失败**不代表方案错误**,只是补丁安装技术问题(竞态+对齐)。
- 复盘 +0x225323C 完整路径:`+0x6CA4E4` 查 watcher → 
  `+0x225318F +0x6C9FEC` → `+0x4FC75C` → `[r15+0x3A0]` 路由链。
  `+0x6CA988` 只做了前半(创建事务),**没有走路由**——这解释了
  为什么 CE 调它只加载了部分 Mod 资源而不刷新玩家 g1m。
- 旧插件崩 `+0x225323C` 的前提是"事件已存在"。加载完成后
  watcher 槽被清空 → 调度器里事件可能已移除 → **现在调用
  `+0x6CA4E4(0x64)` 很可能返回"未找到"→ 走新建分支,安全且完整**。
  这比跳板方案简单一个数量级:一次 execute_code_ex 即可测试。

### 第四轮计划(重启游戏后)

1. 先验证前提:execute_code_ex 调 `+0x6CA4E4(root+0xB98, 静态表条目0)`
   (它是纯查询,CE 线程调用 +0x6CA988 时内部已隐式验证过安全性),
   看返回 0(未找到)还是非 0(已存在)。
2. 若返回 0 → 直接调 `+0x225323C(0x64, 0x33)`(cdecl 2 参),
   观察 LooseFileLoader 是否加载 0x4BA258DF.g1m。
   崩溃风险中低:崩溃点在事件已存在分支,已排除。
3. 若仍崩或无效 → 回到跳板方案,但补丁安装改为
   pause_process → write_bytes → unpause_process,并修栈对齐。

## 2026-08-14 第四~六轮:gate 部署技术成熟 + 全部事后调用路径证伪

### Gate 部署流程(最终成熟版,已验证可复用)

1. `allocate_memory(base_address=模块基址, rwx, 256)` —— gate 必须**靠近模块**
   (CE 默认分配在低地址,rel32 距离超限,jmp 回不去;第 5 轮发现)。
2. Lua 逐字节构建 gate:`push rax..r11 → cmp flag → xchg 抢旗 →
   sub rsp,0x18(栈对齐)→ 设参 → call → add rsp → pops →
   原指令字节 → jmp rel32 回挂点后`。位移全部**手工计算+读回复核**。
   (assemble_instruction MCP 工具只返回字节**不写内存**——第 5 轮教训)
3. `pause_process → write 9字节补丁(E9 rel32 + 4 nop)→ 读回验证 → unpause`。
   挂点选指令中段、栈帧已建立处(canary 已由前序指令算好,不能碰 rax
   直到原指令 store 完;gate 首指令必须是 push,不能是任何 xchg/cmp 变体
   先行 clobber)。第 4 轮崩因:占位 `xchg al,[flag]` 篡改了 canary。

### 第六轮:+0x225323C 在游戏线程 gate 内调用 → 崩溃

gate 参数 ecx=0x64/edx=0x33,call +0x225323C(完整路由链版本)。
部署无崩溃,但触发时游戏死——证实旧结论在正常游戏全局成立:
**事件已注册,`+0x6CA4E4` 返回 0,`[0+0xAD2F]=1` 崩**。
watcher"槽清空"≠事件从调度器哈希表移除。

### 意外发现

`+0x74AA4` 函数(挂点宿主)正常游戏空闲时**不运行**(0 命中),
仅特定场景活跃(上一会话 25k/s 是加载刚完成时)。gate 触发时机
不可控,该点不适合做帧驱动。

### 总结论:事后调用路线全面证伪

六轮实验证明:加载完成后,任何对事件系统子函数的直接调用
(CE 线程/游戏线程/gate 内)都会崩或不生效。事件系统的前置
状态(调用时机/外层对象)不可事后重建。

### 下一步方向(改状态,不调函数)

- gate/插件改为:调 `+0x6CA4E4` 拿**已存在的 watcher**(返回 0 的
  语义需要重读:旧记录说返回0=存在,需确认是否存在分支实际返回
  对象指针),对 watcher 本体做游戏加载时同款操作
  (`[watcher+0xAD2F]=1` 等),让游戏自身流程接力。
- 或:全局版本号失效路线(找 +0x20D20B 消费的版本字段,翻转缓存)。
- 或:F9 模式扩展——既然 UI 路径可行,研究能否在无 UI 时伪造

## 2026-08-14 第七轮:watcher 链表全貌 + body watcher 缺位确认(纯观察)

### 语义修正(推翻旧记录)

`+0x6CA4E4` 完整分支:
- 红黑树/侵入链查找 `+0x6CA514` **找到** → 调 `+0x327769C`(纯状态查询,
  无副作用)→ **返回 0**。返回 0 = 已存在!
- **未找到** → `+0x6CA727` → **自己调 `+0x6CA988` 创建并返回新对象**。
旧文档"事件不存在才返回0/崩溃"方向写反了。+0x225323C 的崩溃是
"已找到,返回 0,[0+0xAD2F] 崩"——但 F9 不崩,因为 F9 时 watcher
真的在链上,返回的是指针。

### 链表结构(已验证,16 桶侵入式链表)

```text
dispatcher = root+0xB98(slot 直接持有对象)
buckets    = [dispatcher+8]        ; 16 桶 × 16 字节
[bucket+0] = 头节点指针(= watcher+0xE0)
[bucket+8] = 计数
节点遍历: [node] 为 next;键在 [node-0xE0](code/sub 两 dword)
插入(+0x6CA778 逻辑): [node]=[bucket]; [bucket]=node; [bucket+8]+=1
hash = ((code<<16|sub)*9 ^ ...) & 0xF   (+0x6CA6DF 公式,可复算)
```

### 关键观察(纯内存读取,零风险)

正常游戏中链上 24 个 watcher,键全是护甲/武器外观 ID
(0x65F34/0x3AD36/0x5CAAE0/0x3B063...)——**没有 0x64 body watcher**。
这证明:加载后 body watcher 被从链表移除 = F9 离开 UI 失效的根因。

### 第七轮崩溃(手抄地址失误,非方案问题)

重放第 1 轮 CE 调用时,slot 地址手抄错误(root+0xB98 算成 root+0x1B98),
传了垃圾指针 → 崩。教训:**所有动态地址必须 Lua 现算,禁止手抄**。

### 下轮实验序列(纯内存操作)

1. Lua 现算 slot = root+0xB98;CE 线程调 +0x6CA988(slot, 静态表条目0)
   拿游离 body watcher 对象(第 1 轮已证此调用 CE 线程安全);
2. 复算 hash → 目标桶;三条写入复刻 +0x6CA778 插入链表;
3. 验证:链表计数+1 且出现 0x64;然后无 UI 状态下触发刷新路径,
   观察 0x4BA258DF.g1m 是否重载。

## 2026-08-14 收工总结(8 轮实验)

### 第八轮:CE 线程重放 +0x6CA988(参数全校验)→ 游戏崩 + CE 卡死

Lua 现算 slot、entry0 读回验证 0x64 均通过后才调用。与第 1 轮
(成功)唯一差异是游戏运行时长。结论:**+0x6CA988 的 CE 线程调用
本身不稳定**(内部 `call [rax+0x28]` 虚表创建依赖随时序变化的全局
状态),第 1 轮成功属侥幸。CE 线程调用路线彻底废弃。

### 确立的知识资产

**结构(会话间稳定,RVA)**:
- 玩家链: [+0x4618398] → root;root+0x11B0 → bodyParent
- 调度器: root+0xB98(对象本体);桶数组 [disp+8],16×16B
- 链表节点 = watcher+0xE0;键 {code,sub} 在节点-0xE0
- 插入算法(+0x6CA778): [node]=[bucket];[bucket]=node;[bucket+8]+=1
- hash 公式可从 +0x6CA6DF 复算
- 静态事件模板表: +0x4376300(条目0 = body {0x64}, 含 GUID)
- watcher 完整生命周期:加载时注册(24个护甲/武器 watcher 在链,
  body watcher 加载后被移除)= F9 离开 UI 失效的根因
- 挂点 +0x74AA4/+0x74AB2: 25k/s 仅特定场景(加载后)活跃,非通用帧驱动

**Gate 部署技术(成熟可复用)**:
近模块 alloc → 手工编码(读回验证)→ pause → 9字节补丁 → unpause。
栈对齐 sub rsp,0x18;首指令必须 push(canary 保护)。
